## 왜 이렇게 나누었는가

### 코어가 Rust인 이유

이 프로젝트의 주장은 "저장 포맷이 정확하다"는 것입니다. 그런데 원래 구현은 브라우저용 파서와
서버용 파서를 같은 JavaScript 파일로 공유하는 방식이었고, 그 공유가 깨지는 순간
`{ } 저장 포맷` 패널이 보여주는 내용과 디스크의 바이트가 갈라집니다. Rust로 옮기면서
그 위험을 구조적으로 없앴습니다 — 파서가 하나뿐이면 갈라질 대상이 없습니다.

부수적으로, 코어가 컴파일된 바이너리에 들어가므로 사용자는 파일 하나만 내려받으면 됩니다.
Node를 설치하라는 안내가 필요 없습니다.

### 왜 WebAssembly까지 만드는가

에디터는 코어를 **동기적으로** 호출합니다. 셀에 값을 입력하면 같은 이벤트 핸들러 안에서
의존 수식이 연쇄 재계산되어야 하고, 문단을 고치면 저장 포맷 패널이 그 자리에서 다시 그려져야
합니다. 이것을 비동기 IPC로 바꾸면 에디터 전체를 프라미스 중심으로 재작성해야 하고, 그 과정에서
중간 상태가 화면에 새는 버그가 생깁니다.

그래서 같은 크레이트를 `wasm32-unknown-unknown`으로 한 번 더 빌드합니다. 복사본이 아니라
**같은 소스의 다른 타깃**입니다. `crates/ai-studio-wasm`은 값을 경계 너머로 옮기는 얇은
`wasm-bindgen` 래퍼일 뿐이고, 로직은 한 줄도 갖지 않습니다.

### 그럼 JavaScript에는 뭐가 남는가

뷰 코드만 남습니다.

| 파일 | 하는 일 | 왜 여기 있는가 |
|---|---|---|
| `apps/web/src/lib/chartSvg.js` | 차트 스펙 → SVG | 그림은 보여주는 쪽에서 그립니다. 디스크에도 `AI.md`에도 SVG는 없습니다 — 다이제스트는 숫자를 표로 싣고, `.pptx`는 네이티브 차트 파트를 씁니다 |
| `apps/web/src/lib/shapeSvg.js` | `prstGeom` 프리셋 → SVG 경로 | 같은 이유. 디스크에는 프리셋 *이름*만 있고, `.pptx`는 그 이름을 그대로 받습니다. 프리셋 **목록**은 Rust에서 읽어오므로 갤러리와 포맷이 어긋날 수 없습니다 |
| `apps/web/src/lib/shapeAdjust.js` | 조절 핸들의 위치와 역함수 | 핸들이 화면 어디에 놓이는지는 그리기 문제입니다. 핸들이 쓰는 `adjust` 값은 포맷이 정의합니다 |
| `apps/web/src/components/TableView.jsx` | 마크다운 표 + 배치 → HTML 표 | 셀 글자는 md에, 배치는 JSON에 — 그리는 것만 뷰의 일입니다 |
| `apps/web/src/lib/markdown.js` | 마크다운 → HTML | 화면 표시용. 저장되는 것은 마크다운 원본입니다 |
| `apps/web/src/doc/paginate.js` | 실측 높이로 페이지 나눔 | 브라우저가 실제로 렌더한 높이가 있어야 하는 계산입니다 |
| `apps/web/src/grid/gridOps.js` | 선택·채우기·병합 같은 편집 조작 | 편집 의도를 셀 변경으로 바꾸는 UI 레이어. 계산 자체는 코어에 위임합니다 |

이 중 어느 것도 **디스크에 저장될 내용을 결정하지 않습니다.** 그 판단은 전부 코어에 있습니다.

### 데스크톱과 서버가 갈라지지 않는 방법

`crates/ai-core`의 `Studio`가 유일한 API 표면입니다. Tauri 커맨드(`crates/ai-studio-app/src/commands.rs`)와
HTTP 라우트(`crates/ai-studio-serve/src/api.rs`)는 각각 한 줄짜리 래퍼이고, 이름도 1:1로 맞춰 두었습니다.

프런트엔드에서는 `apps/web/src/api.js`가 한 곳에서 둘을 나란히 선언합니다:

```js
function call(command, args, http) {
  return isDesktop() ? invoke(command, args) : request(http.path, http.options);
}
```

두 전송 방식을 같은 줄에 적어 두는 것이 어긋남을 막는 가장 싼 방법입니다.

## 기존 Office 파일을 왜 이렇게 다루는가

가져오기는 **한 방향**이다. `.pptx`를 열면 `.aideck` 폴더가 되고 원본은 그대로 남는다.
제자리에서 고쳐 다시 `.pptx`로 저장하는 선택지를 두지 않은 이유는 단순하다 — 그러면 마크다운도,
JSON도, `AI.md`도 없어지고, 이 프로젝트는 느린 PowerPoint가 된다.

세 형식의 충실도는 같지 않고, 같을 수 없다.

| | 무엇이 대응되는가 | 결과 |
|---|---|---|
| `.xlsx` | 거의 전부. 수식은 수식이고, 표시 형식은 표시 형식이다 | 사실상 무손실 |
| `.pptx` | 좌표가 정확히 대응된다 (EMU ÷ 914400 × 96) | 같은 모양으로 보인다 |
| `.docx` | 문단의 *의미*가 대응된다 (제목 단계·목록·인용·표) | 가깝지만 픽셀 단위는 아니다 |

`.docx`가 다른 이유는 이 포맷이 마크다운을 렌더한다는 데 있다. Word의 조판을 픽셀로 재현하려면
마크다운을 버려야 하고, 그러면 에이전트가 읽을 수 있다는 성질을 잃는다. 그래서 문단의 의미를
옮기고 나머지는 근사한다.

### 실제 파일에만 있는 것들

pptx 판독기가 가장 많은 공을 들인 세 곳은 예제 파일에는 없고 실제 덱에는 반드시 있는 것들이다.

* **자리틀 좌표 상속.** 실제 덱에서 제목 도형은 대개 자기 `xfrm`을 갖지 않는다. 레이아웃과
  마스터를 따라가지 않으면 그런 도형이 전부 0,0에 기본 크기로 쌓인다.
* **테마 색.** 대부분의 도형은 색을 직접 말하지 않고 `p:style`로 테마를 가리킨다. 명시적
  채우기만 읽으면 그 도형들이 **투명하게** 들어온다. 눈에 가장 크게 띄는 실패 방식이다.
  (`accent1`을 50% 어둡게 같은 수정자도 적용한다. 계산은 sRGB에서 하므로 Office가 선형 광량에서
  계산한 값과 한두 단계 다르지만, 원본 옆에 놓고 구분할 수 있는 차이는 아니다.)
* **마스터의 글머리 기호.** 본문 문단은 대개 `buChar`를 스스로 말하지 않는다. 마스터의
  `bodyStyle`을 읽되, 레이아웃의 자리틀별 `lstStyle`이 그것을 덮는다 — 부제목의 `buNone`이
  거기 있다. 텍스트 상자는 `otherStyle`을 따르므로 글머리 기호가 없다. 이 세 단계를 다
  거쳐야 "본문에는 붙고 캡션에는 안 붙는" Office의 동작이 된다.

* **글자 크기와 디자인 층.** 앞의 셋과 같은 문제의 더 큰 형태다. 실제 덱에서 44pt는 마스터의
  `titleStyle`에 있고, 띠와 로고는 레이아웃의 도형이며, 배경은 레이아웃의 `p:bg`에 있다.
  슬라이드만 읽으면 문법적으로는 옳고 시각적으로는 남의 문서다. 그래서 판독기는 슬라이드를 읽기
  전에 마스터와 레이아웃의 **자리틀이 아닌** 도형을 낮은 `z`로 먼저 넣고, 텍스트 서식은
  런 → 문단 → 도형 `lstStyle` → 레이아웃 자리틀 → 마스터 순으로 필드 단위로 합친다.
  `showMasterSp="0"`과 `b="0"`처럼 **부정을 말한 것**은 침묵과 구분해서 읽는다 — 구분하지 않으면
  전면 이미지 위에 띠가 그려지고, 굵게를 끈 제목이 다시 굵어진다.

이런 것들은 왕복 테스트로는 잡히지 않는다 (우리 작성기가 그렇게 쓰지 않기 때문에). 그래서
손으로 만든 최소 패키지로 따로 검사한다.

### 수식 엔진을 나눈 방식

`ai-formula`의 `functions.rs`에는 에디터가 살아 있게 하는 핵 — SUM, IF, VLOOKUP과 그 이웃들이
있고, `library/`에는 **남이 쓴 워크북에서 나오는 것들**이 가족별로 있다: `math` · `text` · `date` ·
`stat` · `finance` · `lookup` · `info`. 이름 목록은 각 모듈이 스스로 등록하고, 등록된 이름이 하나도
`#NAME?`을 내지 않는지 테스트가 확인한다. 목록에는 있고 구현이 없는 함수는 수식 입력창이
사용자에게 깨뜨리는 약속이기 때문이다.

`ROW` · `COLUMN` · `INDIRECT` · `OFFSET`은 함수 테이블이 아니라 **평가기 안에** 있다. 이들은 인수의
*값*이 아니라 *주소*를 필요로 하는데, `functions::call`이 받는 것은 이미 평가된 값이라 그때는
`A5`가 숫자 42가 되어 주소가 사라져 있다.

배열 연산자도 평가기에 있다: 범위나 배열이 한쪽에 오면 연산자가 원소별로 적용된다. `SUMPRODUCT((A2:A7="서울")*C2:C7)`은
SUMIFS가 생기기 전 20년간 조건부 합계를 쓰던 방법이고, 이것 없이는 그 수식이 첫 셀만 비교한다.

### 메뉴를 페이지에 그리는 이유

리본은 좁은 창에서 가로로 스크롤되므로 `overflow-x: auto`를 갖고, 그 한 줄이 리본 안의 모든 것을
**두 축 모두** 자릅니다. 색 팔레트를 리본 안에 그리면 리본 높이에서 잘려 절반만 보였다.

그래서 `Popover`는 `createPortal`로 `document.body`에 그리고, 자기를 연 단추의
`getBoundingClientRect()`에 맞춰 `position: fixed`로 붙는다. 위치는 스크롤(캡처 단계)과 리사이즈에
다시 계산한다. 이것이 색 팔레트·도형 갤러리·표 격자가 공유하는 한 곳이고, 새 메뉴를 추가할 때도
잘림을 다시 고민할 필요가 없다.

### 크기를 한 곳에서만 읽는 이유

슬라이드의 크기는 `Slide.canvas` 하나뿐이고, 캔버스·썸네일·슬라이드 쇼·내보내기가 모두 그것을
읽는다. 썸네일 비율만 CSS에 `16 / 9`로 적혀 있었는데, 그 한 줄 때문에 4:3 덱의 썸네일이 늘어나
보였다 — 크기를 두 곳에 적으면 갈라지는 것은 시간 문제라는 것을 보여주는 작은 예다.

### 글꼴을 하나로 정한 이유

원본은 저마다 다른 글꼴을 요구하고, 읽는 사람의 컴퓨터에 그것이 있을 보장은 없다. 글꼴 이름을
블록마다 들고 다니면 **틀린 글꼴을 정확하게 기록하는** 일이 된다. 그래서 포맷의 글꼴은 하나이고,
그 글꼴 파일(Pretendard, SIL OFL 1.1)을 앱이 담아 배포한다. 세 운영체제에서, 네트워크 없이,
에디터와 내보낸 파일에서 같은 모양이 나온다.

대가는 글자 폭이다. 원본에서 한 줄에 꼭 맞던 문장이 한 글자 넘칠 수 있다. PowerPoint가 이미
줄여 넣은 기록(`normAutofit fontScale`)은 반영하지만, 그 외의 줄바꿈 차이까지 맞추려면 글꼴
메트릭을 다시 구현하는 일이 되고, 그것은 글꼴을 하나로 정한 이유를 지운다.

크기의 **기준값**은 스타일시트와 Rust 상수가 한 쌍이다 (`doc::BODY_PX` ↔ `.md--doc`,
`grid::CELL_PX` ↔ 시트 표, `mdblocks::HEADING_EM` ↔ `.md h1`). 가져오기는 "앱이 어차피 그렸을
크기"와 비교해 다른 것만 적고, 내보내기는 같은 상수로 되돌린다. 한 쪽만 바꾸면 문서가 나가면서
크기가 달라지므로, 두 값은 함께 움직여야 한다.

### 없는 기능은 지우지 않고 바꾼다

없는 기능이라고 지우면, 열어 본 사람에게는 그냥 사라진 것이다. 그래서 판독기는 순서대로 시도한다:
**같은 것**(SmartArt → Office가 파일에 함께 그려 둔 도형들), **가장 가까운 것**(방사형 차트 →
꺾은선, 각주 → `¹`와 구분선 아래 문단, 조건부 서식 → 저장된 값 기준의 고정 서식), 그리고 그것도
안 되면 **이름을 대고 알리기**.

여기서 눈에 띄는 판단 두 개:

* **SmartArt는 다시 그리지 않는다.** 도해 레이아웃 엔진을 구현하는 대신, Office가 같은 파일에
  넣어 둔 렌더 결과(`dsp:drawing`)를 읽는다. 이 포맷의 도형과 이름이 같은 요소들이라
  (`dsp:sp` ≡ `p:sp`, 네임스페이스만 다름) 기존 도형 판독기가 그대로 적용된다.
* **조건부 서식은 조건을 잃는다.** 규칙으로 남길 방법이 없으니, 파일이 저장된 시점의 값으로
  판정해 고정 서식으로 굽는다. `expression` 규칙은 수식 엔진으로 셀마다 옮겨 평가하고, 색조는
  두 끝 색 사이를 보간한다. 조건이었다는 사실은 경고로 말한다.

### 옮기지 못한 것은 말한다

`Warnings`가 "SmartArt는 같은 모양의 도형들로 바꿨습니다" 같은 문장을 모아 가져오기 결과와 함께
돌려주고, 런처는 그것을 **열기 전 대화상자**로 보여준다 — Word가 옛 형식을 변환할 때 띄우는 것과
같은 자리다. 토스트로 스쳐 보내면 여섯 줄을 읽을 시간이 없고, 그 여섯 줄이 바로 원본과 다르게
보이는 부분이다.

## 데이터가 흐르는 경로

**저장할 때** (자동 저장은 편집 후 2.5초)

```
에디터 상태 (JS 객체)
  → api.saveProject(folder, project)
  → [데스크톱] Tauri IPC   /  [브라우저] PUT /api/projects/:folder
  → ai_core::Studio::save_project
      · 디스크의 매니페스트를 읽어 보내지 않은 필드를 채움
  → ai_format::project::save_project
      · 항목마다 write_slide / write_section / write_sheet
      · 순서에 맞게 파일 이름을 다시 붙이고, 사라진 항목의 파일을 지움
      · build_digest → AI.md
```

**저장 포맷 패널** (매 편집마다)

```
에디터 상태
  → core/index.js (wasm)
  → ai_format::deck::write_slide  ← 저장 경로와 같은 함수
```

같은 함수를 부르므로 패널과 디스크가 어긋날 수 없습니다.

**표 편집** (행 삽입, 병합, 셀 입력)

```
에디터 상태
  → tableEdit(md, table, op, args)   (wasm)
  → ai_format::table::Table
      · 셀 배열과 merges·cells를 함께 옮김
  → { md, table }  ← 둘이 한 번에 돌아옴
```

행을 삽입하면 `merges`의 범위와 `cells`의 주소가 같이 움직여야 합니다. 이것을 에디터에서 하면
포맷과 에디터 두 곳에 같은 규칙이 생기고, 어긋나면 구멍 난 표가 그려집니다. 그래서 md와 layout을
**한 번의 호출로 함께** 받아 옵니다 — 둘을 따로 패치할 방법을 두지 않는 것이 어긋남을 막는 방법입니다.

**슬라이드 크기 변경** (디자인 탭)

```
너비·높이 px
  → 모든 슬라이드의 canvas를 바꾸고
  → clampBox(block, canvas)   (wasm)   ← 저장 경로와 같은 함수
```

PowerPoint는 크기를 바꿀 때 "최대화 / 맞춤 확인"을 묻는다. 이쪽은 배율을 조정하지 않고 캔버스를
벗어나는 블록만 안으로 들인다 — 저자가 고르지 않은 크기로 글자가 커지는 일이 없는 쪽이다.

**시트 재계산** (셀 입력, 시트 편집)

```
편집된 시트 + 나머지 시트들
  → recalcSheet(sheet, others)   (wasm)
  → ai_formula::evaluate::recalc_sheet_in
      · 시트 이름으로 다른 시트를 찾아 값을 읽음
      · 풀 수 없는 것을 만나면 그 셀의 저장된 값을 남기고 `unresolved`로 보고
  → { cells, changed, errors, unresolved }
```

각 편집 연산도 내부적으로 재계산하지만 자기 시트만 보고 하고, 마지막에 에디터가 워크북 전체로
한 번 더 돌린다. 안쪽 계산이 시트 간 수식을 건드리지 못해도 값을 지우지 않기 때문에(위의 규칙)
두 단계로 나눠도 안전하다.

**용지 크기** (레이아웃 탭)

```
너비·높이 px
  → pageResize(page, w, h)   (wasm)
  → ai_format::model::Page::sized
      · 이름 있는 용지인지 판정 → size
      · 세로 표준형이면 width/height 생략
  → 화면은 pageDims(page)로 되묻는다
```

이름과 크기 중 무엇이 이기는지, 어떤 크기에 이름이 있는지를 에디터가 알아야 할 이유가 없습니다.
`사용자 지정`이라는 라벨조차 코어가 돌려줍니다.

**셀 편집** (매 키 입력)

```
입력 문자열
  → parseCellInput (wasm)  → 셀 객체
  → recalcSheet   (wasm)   → 의존 수식 연쇄 재계산
  → 화면 갱신
```

디스크도, 서버도 관여하지 않습니다.

## 이식할 때 고친 것

원래 JavaScript 구현을 그대로 옮기는 것을 기본으로 했지만, 옮기는 과정에서 드러난 결함은
그대로 재현하지 않았습니다. 각각 테스트가 붙어 있습니다.

| 무엇 | 원래 동작 | 지금 | 테스트 |
|---|---|---|---|
| `.docx` 용지·여백 | `TWIP(PT(px))` 로 두 번 변환해 모든 페이지가 75% 크기로 나갔습니다. A4가 Word에서 6.2인치 | A4 = 8.27인치 | `office.rs::a_doc_exports_to_a_well_formed_docx` |
| 수식 참조 이동 | 참조 패턴에 경계 검사가 없어 `=LOG10(A1)` 을 아래로 채우면 함수 이름이 `LOG11` 로 손상 | 함수 이름은 건드리지 않습니다 | `refs.rs::function_names_are_not_references` |
| 마크다운 표 재가져오기 | `\|` 를 이스케이프해 쓰면서 읽을 때는 모든 `\|` 로 분리해, `a \| b` 가 `a \` 로 잘림 | 이스케이프된 구분자를 존중합니다 | `grid.rs::escaped_pipes_survive_the_projection` |
| `TODAY()` | `Math.round` 로 반올림해 UTC 정오 이후에는 내일 날짜를 반환 | 오늘 날짜 | `functions.rs` |
| `.cells.json` 키 순서 | `f, t, fmt, v` — `docs/FORMAT.md` 의 스펙과 불일치 | 스펙대로 `f, v, t, fmt` | 왕복 테스트 |
| `PUT /api/projects/:folder` | 매니페스트 전체를 되돌려 보내야 했습니다 | 보낸 부분만 반영, 나머지는 디스크 값 | `e2e.mjs` |
| 마크다운 표의 정렬 행 판정 | `\|   \|   \|` 를 정렬 행으로 인식해, **빈 행이 있는 표를 재가져오면 그 아래 행이 한 칸씩 밀렸습니다** | 정렬 행은 대시를 포함해야 합니다 | `grid.rs::a_blank_row_in_a_projection_is_not_swallowed` |
| 날짜 셀의 타입 | 재계산이 `t: "d"` 를 `"n"` 으로 되돌려, **열 요약이 날짜 일련번호를 합계에 넣었습니다** | 값이 담을 수 없는 정보이므로 유지합니다 | `evaluate.rs::recalculating_keeps_a_date_a_date` |
| 셀 안의 이스케이프된 `\|` | 저장할 때마다 백슬래시가 하나씩 늘어났습니다 | 읽을 때 풀고 쓸 때 씌웁니다 | `table.rs::a_pipe_inside_a_cell_survives_any_number_of_saves` |
| pptx 표의 병합 연속 셀 | 한 행짜리 병합에도 `hMerge`와 `vMerge`를 모두 켰습니다 | 실제로 이어지는 축만 켭니다 | `table.rs::a_single_row_merge_continues_only_horizontally` |

이식 시점에 **의도적으로 미뤄 두었던 동작** 둘은 이후에 고쳤습니다. 둘 다 "저장을 반복하면
바뀌지 않은 문서의 diff가 조용해야 한다"는 이 포맷의 약속에 관한 것입니다.

1. **Doc의 `outline[].anchor` 가 저장할 때마다 바뀌었습니다.** 서식이 없는 문단은
   `<!-- block:id -->` 앵커를 갖지 않으므로 안정적인 id가 없고, 열 때마다 새 id를 받습니다.
   지금은 앵커를 블록 id가 아니라 **제목 텍스트에서 유도**합니다 (`핵심 성과` → `핵심-성과`,
   중복은 `-2` · `-3`) — `FORMAT.md` 가 처음부터 말하던 형태이고, 제목을 고치지 않는 한 저장을
   반복해도 바뀌지 않습니다 (`doc.rs::outline_anchors_are_stable_across_saves`).
2. **Deck의 `layout.json` 이 기본값과 같은 스타일까지 썼습니다.** Doc의 "기본값과 같은
   오버라이드는 정보가 없으므로 버린다"는 규칙을 Deck의 텍스트 블록에도 적용해, `valign: "top"`
   같은 항목이 더 이상 모든 블록에 들어가지 않습니다. 읽을 때 기본값이 다시 병합되므로 잃는
   것은 없습니다 (`deck.rs::default_equal_style_entries_stay_out_of_the_layout`).

## 이 환경에서 검증한 것과 하지 못한 것

**검증했습니다**

- Rust 449개 · 웹 85개 · e2e 100개 · UI 스모크 291개
- 커밋된 샘플(`templates/`)을 읽어 다시 쓴 결과, **바뀌는 것은 `manifest.json` 의 `modified`
  타임스탬프뿐입니다** (`cargo run -p ai-format --example roundtrip -- templates /tmp/out`).
  이식 직후에는 JSON 쪽에 세 종류의 차이가 더 있었지만 — 저장마다 바뀌는 `outline[].anchor`,
  스펙(`f, v, t, fmt`)과 어긋난 JS의 키 순서, 기본값과 같은 `valign: "top"` — 앞의 것 둘은 포맷을
  고치고(위 참고) 스펙 위반은 스펙대로 맞춘 뒤 샘플을 재저장해, 이제 저장이 남기는 diff는 저장
  시각 하나입니다.
- 만들어진 `.xlsx` · `.pptx` · `.docx` 를 `openpyxl` · `python-pptx` · `python-docx` 로 열어 확인:
  살아있는 수식, 표시 형식, 틀 고정, 이름 범위, 네이티브 차트의 계열·항목, A4 용지와 여백, 제목 스타일
- **반대 방향도**: 같은 라이브러리들로 다른 구현이 만든 pptx · docx · xlsx 를 생성해 가져오기에 넣고,
  수식·서식·병합·틀 고정·이름 범위, 자리틀 상속 좌표, 테마 색, 도형 프리셋, 표 병합, 차트 숫자,
  목록 단계가 넘어오는지 확인
- 모든 OOXML 파트의 XML 적합성과 `_rels` 참조 정합성

**하지 못했습니다**

- **Tauri 데스크톱 앱을 실제로 실행하지 못했습니다.** 이 개발 환경(Amazon Linux 2023, aarch64)에
  `webkit2gtk` 패키지가 없습니다. 타입 검사(`cargo check`)는 pkg-config 스텁으로 통과시켰지만
  링크와 실행은 CI 러너에서 처음 일어납니다. `.github/workflows/release.yml` 이 세 OS 모두를 빌드합니다.
- **브라우저에서 눈으로 확인하지 못했습니다.** headless 브라우저를 실행할 시스템 라이브러리가 없어
  렌더링 검증은 jsdom까지입니다.
